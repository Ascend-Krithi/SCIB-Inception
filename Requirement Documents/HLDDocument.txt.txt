High-Level Design Document

1. Introduction
This High-Level Design (HLD) covers the "Parent can allocate and manage funds for a youth account" feature as described in ADR SCIB-25 and its linked implementation records. The solution enables parents/guardians to teach financial responsibility by allowing them to allocate funds, set spending limits, and monitor spending for youth accounts in a secure, compliant, and user-friendly manner.

2. System Overview
The system extends the banking platform to support:
- Parent login and dashboard access for youth accounts
- Secure fund transfers from parent to youth accounts
- Weekly spending limit configuration for youth
- Real-time transaction activity viewing
- Robust error handling (e.g., insufficient funds, invalid inputs)
- Compliance with security and regulatory standards

4. Component Design
- Parent Dashboard UI (SCIB-195): Summary, actions, limits, transactions
- Fund Transfer UI/Flow (SCIB-194): Source selection, amount, validation, confirmation
- Spending Limit UI/Flow (SCIB-196): Limit input, edit, validation, guidance
- Transaction Activity UI (SCIB-197): List, filters, scan-friendly, desktop/tablet
- API Layer: Implements endpoints (SCIB-26, SCIB-27, SCIB-28, SCIB-29, SCIB-30)
- Account/Transaction Services: Core data, business rules, validation
- Notification Service: Parent notifications (limits, errors)
- Security Layer: OAuth, RBAC, input/output validation

ADRs mapping: Each component references the acceptance criteria and implementation details of the corresponding ADR/subtask.

5. Data Design
- Accounts: Parent and youth linked by parent_id
- Transactions: Linked to youth account, with merchant, amount, date, type
- Settings: Weekly limit, updated timestamp
- All schemas as per OpenAPI definitions (see API Contract Outline)

6. Interface Design
- RESTful APIs (see API Contract Outline)
- UI: Responsive React components for dashboard, transfer, limits, activity
- Integration: Core banking, notification service

7. Non-Functional Aspects
- Security: OAuth 2.0, RBAC, input/output validation, audit logging
- Compliance: GDPR, PCI-DSS, ISO 27001
- Performance: API <500ms, UI responsive <1s, horizontal scaling
- Scalability: Supports 10,000+ concurrent parent logins
- Availability: 99.99% uptime, active-active deployment
- Reliability: Automatic failover, data consistency
- Maintainability: Modular, OpenAPI, C4 documentation
- Auditability: All parent actions logged
- Disaster Recovery: RTO 4h, RPO 1h
- Backup: Daily, encrypted, off-site
- Monitoring: Real-time, alerts on failures
- Logging: Centralized, structured logs
- RBAC: Roles for parent, youth, admin

8. Integration
- Core Banking System: Account/transaction APIs
- Notification Service: Alerts for limit breach, failed transfer
- OAuth Provider: User authentication

9. Deployment
- Dockerized containers for API/UI
- Kubernetes for orchestration and scaling
- CI/CD pipeline for build, test, deploy
- Blue/green deployment for zero downtime
- Secrets managed via vault

10. Test Strategy
- Automated API tests (unit/integration)
- UI E2E tests (Selenium/Cypress)
- Negative/boundary/concurrency tests (see SCIB-1866, SCIB-1882, SCIB-1884, SCIB-1896)
- Manual UAT

11. Cross-Cutting Concerns
- Input validation, output filtering (all APIs)
- Audit logging (all parent actions)
- RBAC enforced via middleware
- Data masking for PII in logs
- Monitoring and alerting (API, infra, business events)

12. Implementation Strategy
- Phase 1: Dashboard, fund transfer, transaction viewing
- Phase 2: Spending limit UI/API, enforcement, notifications
- Phase 3: Advanced error handling, audit, compliance
- Dependencies: Core banking APIs, notification integration, OAuth

13. Technical Risks
| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| Core banking API latency | Medium | Medium | Caching, async UI loading |
| Race conditions on balance update | High | Medium | DB transactions, optimistic/pessimistic locking |
| Notification delivery failure | Low | Low | Retry, alert fallback |
| Regulatory change | Medium | Low | Config-driven rules, compliance review |
| Data privacy breach | High | Low | Strong RBAC, encryption, audit logging |

14. Technical Debt
- Deferred: Multi-language UI, advanced reporting, mobile app parity
- Documented in backlog

- ADR mappings: All requirements and design decisions traceable to SCIB-25 and subtasks (SCIB-194, SCIB-195, SCIB-196, SCIB-197)

API Contract Outline

Endpoint: GET /api/youth-accounts/{youthAccountId}/dashboard
- Method: GET
- Request Params: youthAccountId (path)
- Response:
  {
    "youthAccountId": "string",
    "accountBalance": "decimal",
    "spendingLimit": "decimal",
    "currency": "string",
    "recentTransactions": [
      {
        "transactionId": "string",
        "date": "datetime",
        "description": "string",
        "amount": "decimal"
      }
    ]
  }
- Error Handling: 403 Unauthorized, 404 Not Found, 500 Internal Server Error

Endpoint: POST /api/youth-accounts/{youthAccountId}/fund-transfer
- Method: POST
- Request Body:
  {
    "sourceAccountId": "string",
    "transferAmount": "decimal",
    "currency": "string"
  }
- Response:
  {
    "transferId": "string",
    "status": "SUCCESS|FAILED",
    "updatedBalance": "decimal"
  }
- Error Handling: 400 Bad Request (validation/insufficient funds), 403 Unauthorized, 500 Internal Server Error

Endpoint: PUT /api/youth-accounts/{youthAccountId}/spending-limit
- Method: PUT
- Request Body:
  {
    "weeklyLimit": "decimal"
  }
- Response:
  {
    "youthAccountId": "string",
    "weeklyLimit": "decimal",
    "status": "UPDATED"
  }
- Error Handling: 400 Bad Request (validation), 403 Unauthorized, 500 Internal Server Error

Endpoint: GET /api/youth-accounts/{youthAccountId}/transactions
- Method: GET
- Query Params: startDate, endDate, page, pageSize
- Response:
  {
    "transactions": [
      {
        "transactionId": "string",
        "date": "datetime",
        "merchant": "string",
        "amount": "decimal",
        "transactionType": "debit|credit"
      }
    ],
    "pagination": {
      "page": "number",
      "pageSize": "number",
      "totalRecords": "number"
    }
  }
- Error Handling: 403 Unauthorized, 404 Not Found, 500 Internal Server Error

Error Responses (All APIs):
- 400: { "error": "Validation error details" }
- 403: { "error": "Unauthorized" }
- 404: { "error": "Resource not found" }
- 409: { "error": "Conflict (e.g., duplicate transaction)" }
- 500: { "error": "Internal server error" }

RBAC:
- Only parent/guardian with valid session can access/manage youth account APIs
- Youth may access own account data (read-only)
- Admins can audit but not initiate transfers

Non-Functional Requirements (NFRs)

1. Security
- OAuth 2.0 authentication for all APIs
- RBAC: Parent/guardian, youth, admin roles
- Input validation, output filtering on all endpoints
- Audit logging of all parent actions
- Data encryption at rest (AES-256) and in transit (TLS 1.2+)
- Data masking for PII in logs
- Regular security penetration testing

2. Compliance
- GDPR: Data subject rights, consent, deletion
- PCI-DSS: Secure handling of payment data
- ISO 27001: Information security controls

3. Performance
- 95% of API requests <500ms
- UI interactions <1s
- Bulk operations (e.g., transaction history) paginated, <2s

4. Scalability
- Supports 10,000+ concurrent parent logins
- Horizontal scaling for API/UI tiers

5. Availability
- 99.99% uptime SLA
- Active-active deployment in two regions

6. Reliability
- Automatic failover for DB and API
- Data consistency enforced (ACID)

7. Maintainability
- Modular codebase, OpenAPI/C4 documentation
- CI/CD with automated testing

8. Auditability
- All fund transfers, limit changes, dashboard accesses logged
- Immutable audit trail (WORM storage)

9. Disaster Recovery
- RTO <4 hours, RPO <1 hour
- Quarterly DR drills

10. Backup
- Daily, encrypted, off-site backup
- Backup restore tested quarterly

11. Monitoring
- Real-time API, infra, and business event monitoring
- Automated alerting on error spikes, SLA breaches

12. Logging
- Centralized, structured logs (JSON)
- Correlation IDs for traceability

13. RBAC
- Roles: parent, youth, admin
- Enforcement at API gateway and application layer
- Regular RBAC review

14. Enterprise Compliance
- Input validation, output filtering, audit logging, RBAC enforced across all APIs and UI flows
